# Migrate selected repositories to shared methods

Use only for an authorized migration of named Systems/Projects or their seeds.
Package installation alone does not authorize repository writes. Inspect local
AGENTS, branch, dirty state, active work and current generic callers first.

Inventory each candidate's contents and ownership. Legacy generic Spec, Build,
Review, Ship, technology choice, repository audit and tracking copies belong in
the shared plugin. A design review, content graph audit or other domain method
may be correctly specialist-owned despite a similar name; preserve it.

Capture exact base commits and recoverable bytes for overlapping local changes.
Compare old generic bodies with current shared responsibilities and move any
actual repository-specific requirements to AGENTS or their existing domain
source. Remove only established generic payloads and update callers to native
skill names, never cache paths, wrappers or symlinks. Check links, specialist
preservation and the repository's affected validations. Template generators
must emit local contracts and specialist space without generic phase copies.

Use isolated reviewable commits. An active or dirty checkout needs explicit
scoped reconciliation: precompute the merged instruction changes, preserve
unrelated bytes and reject concurrent drift or ambiguous conflicts. Never stash,
reset, clean or publish unrelated work to make adoption pass. If safe local
adoption cannot be verified, retain the reviewed commit and report the pending
root; package success is not repository migration proof.

At the task boundary, verify installed shared-method identity and fresh
repository discovery. Loaded sessions may retain old instructions until a fresh
context; report that separately. Record base/new commits, preserved specialists,
checks and remaining gaps. Git can recover tracked removed methods; it cannot
restore untracked artifacts that were not separately preserved.
